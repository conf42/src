# When API Tests Aren’t Enough: End-to-End Testing a Live Dota 2 Data Pipeline

A talk at [Conf42 Chaos Engineering 2026](https://www.conf42.com/chaos2026) by [Egor Kolovertnykh](https://www.conf42.com/speaker_Egor_Kolovertnykh) (Senior Backend Developer @ Betboom). Page: https://www.conf42.com/Chaos_Engineering_2026_Egor_Kolovertnykh_dota_pipeline_testing

## Abstract

In the high-stakes world of live esports broadcasting, showing incorrect draft data in a live widget isn't just a bug — it's a ruined viewer experience. To deliver real-time Dota 2 pick/ban data, we built a complex pipeline relying on Game State Integration (GSI). This system takes state snapshots, restores sequence events, maps internal entities, and pushes updates via WebSockets to a frontend widget.  We quickly realized that traditional unit and integration tests were insufficient. We could validate parsing, mappings, and WebSocket contracts, but a correct HTTP payload didn't mean a correct widget. A hero identifier could be mapped perfectly in code, but still display the wrong asset on the screen.  In this talk, I will share how we bridged the gap between protocol correctness and product correctness. Instead of relying on artificial JSON fixtures, we turned the actual Dota 2 client and known game replays into our primary E2E test fixture. You'll learn how to test an entire delivery chain — from raw game data to network transport and frontend rendering — in a single loop, and how we empower operators with a "Test to Live" config check to prevent production disasters caused by unexpected game mode semantics.  Ultimately: if the user sees the widget, the widget is what you should test.
