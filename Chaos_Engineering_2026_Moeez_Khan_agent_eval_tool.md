# Your AI Agent Passed Every Eval. What Happens When a Tool Call Times Out?

A talk at [Conf42 Chaos Engineering 2026](https://www.conf42.com/chaos2026) by [Moeez Khan](https://www.conf42.com/speaker_Moeez_Khan) (Software Development Engineer @ AWS). Page: https://www.conf42.com/Chaos_Engineering_2026_Moeez_Khan_agent_eval_tool

## Abstract

[Disclaimer: The opinions, insights, and perspectives shared in this session are solely my own and do not reflect those of my current or past employers, nor do they convey any confidential information by any means.]  Overview: Chaos engineering taught us not to trust the happy path for services. Agents need the same discipline. When an agent's tool call times out, the write may already have committed, and a retry may become a duplicate charge. When a read-back is stale, the agent may "repair" something that was never broken. When a call returns ok after half the work, the agent reports done. None of this shows up in an eval where every tool answers cleanly, and every one of these faults is routine in production.  Structure: Part 1: The steady state is the real state, not the agent's report. Chaos experiments start from a steady-state hypothesis. For an agent, that hypothesis has to be written against the backend (exactly one charge, fulfillment applied), and the agent's own claim gets scored separately. Two numbers, not one: what landed, and what the agent said landed.  Part 2: A fault taxonomy for tool calls. Timeout after commit, delayed visibility, partial success, and stale conflicts, injected at low, medium, and high rates taken from published failure measurements (Mansoor et al.). Where to inject them: in the tool, in a proxy between the agent and an MCP server, or in the backend. How to keep the blast radius small: seeded faults, sandboxed state, and containers for any third-party tool.  Part 3: Metrics that a clean run hides. Duplicate-action rate, silent-failure rate (reported success, wrong state), an explicit "unconfirmed" rate, and pass^k, the chance a task succeeds k times in a row. In agent-fault-lab (MIT), 3,200 seeded episodes per row: an idempotency key alone still left 9.9% silent failures; a read-back alone was fooled by delayed visibility; only a key plus a polled postcondition check plus an "unconfirmed" outcome held at 0.0% silent failures and 98.5% pass^8. These are scripted policies, labelled as such, and the harness is how you measure your own agent.  Part 4: Demo and game day. A live run: inject a lost response, watch a retry agent report success while the ledger shows two charges, then rerun the same seed against the verified design. We close with a one-page game-day plan for an agent team.  Attendees leave with: 1. Steady State Against Real State: score what landed and what the agent claimed as two separate numbers 2. The Tool-Call Fault Taxonomy: four faults, three intensities, and where to inject each one 3. pass^k Over pass@1: one clean run proves almost nothing about an agent you'll run thousands of times 4. The Unconfirmed Outcome: give the agent a sanctioned "I can't confirm it" instead of a confident guess 5. A Harness to Run Today: agent-fault-lab, standard library only, no API keys  A green eval only tells you the agent works when nothing fails. Production is where things fail.  Sources: 1. agent-fault-lab (results table and method): https://github.com/MuhammadMoeezKhan/agent-fault-lab 2. Mansoor, Phadke, Rana, "Verified Tool Calls Improve LLM Agent Reliability Under Non-Atomic Failures," arXiv:2608.02645, 2026 (fault types and rates). 3. tau-bench, the pass^k estimator (Yao et al., 2024).
