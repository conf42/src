# Database DevOps: CD for Stateful Applications

Conf42 Blog, 2026-06-04. https://www.conf42.com/blog/2026-06-04-harness

## Database DevOps: Bringing Continuous Delivery to Stateful Applications

Modern software delivery pipelines are remarkably good at deploying stateless applications. Teams can push application updates multiple times a day, automate testing, validate rollouts, and quickly roll back when something goes wrong.

Databases are often a different story.

While application deployments have embraced continuous delivery, database changes frequently remain manual, infrequent, and high-risk. Many organizations that deploy application code daily still schedule database releases monthly or quarterly because schema changes introduce challenges that traditional CI/CD workflows struggle to address.

In his session *Database DevOps: CD for Stateful Applications*, Stephen Atwell explored how engineering teams can apply modern delivery practices to databases, making stateful systems just as testable, repeatable, and automatable as the applications that depend on them.

### Why Databases Remain a Deployment Bottleneck

The core challenge of database delivery is state.

Stateless applications can be replaced, scaled, or rolled back relatively easily because their state lives elsewhere. Databases contain the data that applications depend on, making every structural change potentially risky.

Simple schema updates can become surprisingly complex when applications remain online throughout the deployment process.

Consider a scenario where a single database column needs to be split into multiple fields. During deployment, both the old and new versions of the application may run simultaneously. If each version reads and writes data differently, inconsistencies can emerge immediately.

This challenge often forces teams into maintenance windows, deployment freezes, or highly manual release processes.

As a result, database changes frequently become the limiting factor in otherwise mature continuous delivery environments.

### Continuous Delivery Requires Backwards Compatibility

Modern deployment patterns such as blue-green and canary releases depend on running multiple versions of an application simultaneously.

This creates a requirement that many database migrations fail to consider: backwards compatibility.

If version A of an application and version B of an application are both serving traffic, the underlying database must support both versions throughout the transition.

Database changes therefore cannot simply focus on the final desired schema. They must also account for the intermediate states that exist while deployments are in progress.

Successful database delivery requires teams to think about migrations as a series of controlled steps rather than a single change.

### The Hidden Complexity of Zero-Downtime Database Migrations

Zero-downtime deployments are relatively common at the application layer. Achieving the same outcome at the database layer is significantly harder.

The challenge becomes particularly apparent when restructuring data.

During the session, Atwell demonstrated a migration that transformed a PostgreSQL table storing serialized JSON data into a properly structured relational schema.

The goal was straightforward: extract fields from a JSON document and store them in dedicated database columns.

The execution, however, required careful planning.

The migration needed to ensure:

- No downtime
- No data loss
- Full backwards compatibility
- Support for old and new application versions
- Safe rollback capabilities

Achieving all of these requirements simultaneously demands more than simply writing migration scripts.

### Using Database Triggers to Maintain Consistency

One of the key techniques demonstrated during the session involved database triggers.

When introducing new columns, the existing application still expects the original data structure. New application versions, meanwhile, expect the updated schema.

Rather than forcing an immediate switch, synchronization mechanisms can keep both representations aligned.

In the demonstrated migration, triggers ensured that updates to the original JSON field automatically updated the new relational columns.

Additional triggers performed the reverse operation, keeping the original structure synchronized whenever the new schema was modified.

This approach allowed both versions of the application to operate simultaneously while observing the same data.

By maintaining consistency in both directions, teams gain the flexibility needed to deploy, test, validate, and roll back safely.

### Large Data Migrations Require More Than Correct SQL

Database migrations often fail not because the migration logic is incorrect, but because operational realities are ignored.

A script that performs well on a development database may behave very differently against production datasets.

Tables may contain millions or billions of rows. Long-running transactions can create lock contention, impact performance, or introduce unexpected downtime.

For this reason, migration strategies must account for scale from the beginning.

Instead of processing entire datasets in a single transaction, modern migration workflows often break work into smaller batches that can execute incrementally and safely.

This reduces risk while allowing migrations to proceed without disrupting production workloads.

### AI-Assisted Database Development

One of the more interesting aspects of the demonstration was the use of generative AI to create migration logic.

Rather than manually writing complex PostgreSQL migration code, the schema transformation was generated through natural language prompts.

The generated migration created new columns, built synchronization triggers, and produced the necessary data migration logic.

While AI-generated code still requires validation, it introduces a new workflow for database teams.

Instead of spending hours building migration scripts manually, engineers can focus on reviewing, validating, and testing generated solutions.

The result is a faster iteration cycle while still maintaining governance and operational controls.

### Governance Matters as Much as Automation

Automation alone does not make database deployments safe.

Every automated process still requires guardrails.

Throughout the deployment workflow demonstrated during the session, database changes passed through governance checks before being applied.

These checks verified that deployments complied with predefined policies and prevented potentially destructive operations from reaching production environments.

Examples include:

- Preventing accidental data loss
- Blocking unsafe schema operations
- Enforcing deployment policies
- Creating rollback checkpoints
- Validating generated SQL before execution

As organizations increase deployment velocity, governance becomes increasingly important because manual review alone cannot scale indefinitely.

### Testing Database Changes Against Production Data

One of the biggest challenges in database testing is reproducing production behavior.

Many database issues only appear when migrations encounter real customer data, realistic workloads, or unusual edge cases.

Traditional testing environments often fail to capture these conditions.

To address this challenge, Atwell demonstrated a workflow that clones production data into staging environments before running migration tests.

This approach allows teams to validate schema changes against realistic datasets while still operating within controlled environments.

When combined with automated testing, production-like data significantly improves confidence in deployment outcomes.

Organizations implementing this strategy must ensure that security controls, access policies, and compliance requirements remain consistent between production and staging environments.

### Verifying Data Consistency During Deployment

Testing database migrations requires more than simply checking whether a deployment completed successfully.

Teams must verify that data remains consistent throughout the transition.

In the demonstrated workflow, automated tests interacted with both the old and new versions of the application.

Actions performed through one version were immediately validated through the other version.

This process confirmed that both applications continued to observe identical data despite significant schema changes occurring underneath them.

These consistency tests become especially valuable when supporting parallel deployments through blue-green or canary release strategies.

Without this validation, subtle synchronization issues can remain hidden until they affect production users.

### Combining Database Migrations with Progressive Delivery

Application delivery practices such as blue-green deployments and canary releases have become common across cloud-native environments.

Database changes can benefit from the same principles.

During the session, schema updates were deployed alongside controlled application rollouts.

In staging environments, blue-green deployments allowed old and new versions to operate simultaneously while automated tests verified compatibility.

In production environments, canary deployments gradually increased traffic to the new version while monitoring system health and behavior.

This progressive approach reduces risk by limiting exposure and creating multiple opportunities to detect issues before they impact all users.

### The Future of Database Delivery

For years, databases have been treated as a special case within software delivery pipelines.

Application teams embraced automation while database changes remained manual, infrequent, and operationally risky.

That distinction is beginning to disappear.

Advances in infrastructure automation, Kubernetes-native workflows, AI-assisted development, automated testing, and database-focused CI/CD tooling are making it possible to manage stateful systems using many of the same practices that transformed application delivery.

The goal is not simply faster deployments.

It is creating a delivery process that is more predictable, more repeatable, easier to test, and safer to operate.

### Bringing Stateful Applications into Modern CI/CD

Database delivery will always require additional care because data cannot simply be redeployed when something goes wrong.

However, that does not mean databases must remain outside modern delivery practices.

By combining backwards-compatible schema changes, automated testing, governance controls, production-like environments, and progressive deployment strategies, organizations can bring databases into the same continuous delivery workflows that already power their applications.

The result is a more unified software delivery process where both application code and data evolve together, safely and repeatedly, without sacrificing reliability or availability.
