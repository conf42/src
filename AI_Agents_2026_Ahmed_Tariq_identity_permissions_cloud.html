    Abstract

    An AI agent that can inspect logs, call cloud APIs, run infrastructure commands, or trigger a deployment is no longer just answering questions. It is participating in production operations. The easiest prototype gives the agent a shell and a broadly privileged credential. A safer architecture gives it a small set of typed tools, a deliberately limited identity, and enforcement that sits outside the model. This talk presents a practical design for cloud operations agents using patterns already used to secure CI/CD automation: separate identities for observation and execution, read-only access by default, short-lived credentials through workload identity federation, and state-changing actions placed behind plan, policy, and approval stages. It will also cover failure modes that access control alone cannot prevent, including invalid tool arguments, repeated or partial execution, unsafe retries, timeouts, and missing audit context. Every tool call should be recorded as a production change event, with the agent identified as the actor. Finally, the talk examines prompt injection through operational data. Logs, tickets, alert descriptions, and commit messages may contain attacker-controlled text, so agents must treat them as untrusted data rather than instructions. These patterns come from securing privileged automation in real cloud environments. The principle throughout is simple: an agent’s capability is defined by its tools and credentials. Keep both small. Cloud operations agents should not receive an unrestricted shell and a powerful service account. This talk covers typed tools, split read and execute identities, short-lived credentials, plan-first actions, policy-enforced approvals, safe retries, complete auditing, and defences against prompt injection through logs and tickets.
