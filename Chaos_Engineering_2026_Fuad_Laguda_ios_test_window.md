# The value that is eventually right: a tenth-of-a-second window on iOS, and why every test that waits cannot see it

A talk at [Conf42 Chaos Engineering 2026](https://www.conf42.com/chaos2026) by [Fuad Laguda](https://www.conf42.com/speaker_Fuad_Laguda) (Customer Sales Advisor @ Sky). Page: https://www.conf42.com/Chaos_Engineering_2026_Fuad_Laguda_ios_test_window

## Abstract

Ask a phone for a portrait video in the browser and the file comes back sideways. I spent three nights assuming it was my code. Then I built a test page and it said there was no bug, four times in a row. The one fact that would not fit: the same phone, in the same ten minutes, still recorded sideways when the fix was off.  The cause is a window. For the first 112 to 139 milliseconds the camera track reports the sensor's landscape size, then corrects itself at the first painted frame. Read inside the window and you get the wrong shape. Read after it and everything is fine. Every one of my clean tests waited for the preview before reading, which put it on the safe side of the window every time. A test written without knowing the window exists cannot see the bug, no matter how carefully it is written.  That is a resilience story, not a camera story. Any value that is eventually right will pass a test that waits for things to settle, and fail in production for the code that did not wait. A fixed delay is not a fix, it is a race you will eventually lose that also taxes every user who did not need it. The signal you want is the event that makes the value true, not the clock.  This talk is the measurement, taken on a real iPhone with timing tables, what the failure looked like inside a production SDK that had carried the bug for thirteen months with three reporters, and what happened when the window was written down: Apple's WebKit team triaged the report as a regression the next day, and LiveKit shipped one fix in six hours and a second four days later from a gap I found reviewing the first.  What the talk covers, pre-recorded, about 30 minutes:  1. The symptom, two clips from the same phone, fix off and fix on. 2. Four clean test runs and the fact that would not fit. How a test settles onto the wrong side of a window. 3. The measurement. Read the value the moment it exists and keep reading. 1920 by 1080 at once, 1080 by 1920 at the first frame, 112 ms and 139 ms across two runs. Why the number moves with device, camera, resolution and load. 4. The production failure. A year-old issue in a widely used video SDK: a 10 ms sleep, then poll until the value exists. It exists immediately and it is wrong, so a portrait phone announces itself as landscape to everyone on the call. 5. Why a longer sleep is not the fix. Two runs, two numbers. Any constant is a race. 6. Two fixes with code: wait for the event that makes the value true, or measure the truth directly and never trust the report. 7. How to write the test that would have caught it, and the general rule: name the event that makes your value true, and gate on that, never on time. 8. What happened when the window was written down. Report to first fix in six hours, second fix in four days.  Takeaways: an eventually-correct value passes every test that waits. Gate on the event, not the clock. When a report and the real thing disagree, the real thing is the evidence. Measure the window before you argue about the delay.
