# One flag, no deploy: switching diagnostics and providers at runtime in a one-person production app

A talk at [Conf42 Feature Flags 2026](https://www.conf42.com/featureflags2026) by [Fuad Laguda](https://www.conf42.com/speaker_Fuad_Laguda) (Infrastructure Engineer @ Independent, Stirling). Page: https://www.conf42.com/Feature_Flags_2026_Fuad_Laguda_flag_diagnostics_runtime

Video: https://www.youtube.com/watch?v=eHhQaCSaqqY

## Abstract

I run two production web apps alone. When something goes wrong at eleven at night I cannot ship a build with more logging and wait. So the diagnostics live behind a flag in Cloudflare KV: off, admin only, or everyone, flipped in seconds and read on every request. The same shape controls the writer: after four consecutive failures from the primary language-model provider the app hands off to a second provider on another cloud, and the flag tells me when it did. This talk is the small, boring machinery of that: how the flag is read without adding latency, what the "admin only" state is for and what it costs, why the failover threshold is four and not one, and a deliberate failover test, forced on purpose on 24 September 2026 with the trace switched on, what it recorded, and what I changed after. Nothing here needs a platform team. It needs one key in a KV store and the discipline to leave the switch off.  **Outline**, pre-recorded, 25 to 30 minutes. 1. The app and the constraint: one engineer, two products, no on-call rota but me. 2. The trace flag: three states in KV, how each request reads it, what each state logs, the cost of leaving it on. 3. The admin-only state: raising diagnostics for one account while every other user sees nothing. 4. The writer failover as a flag: the four-failure trigger, the second provider, what the flag records on handoff. 5. The deliberate test of 24 September 2026: forcing the trigger, the timeline, the output quality on the fallback, what changed. 6. Rules I keep: flags are read, never cached past a request. Every flip is dated in a file. The switch goes off when the work is done.  **Takeaways.** A three-state flag (off, admin, all) is worth more than a boolean for diagnostics. Read flags per request from a store built for it and the latency is nothing. A provider failover is a flag with a counter. Test the failover on purpose before it tests you. Turn it off when you are done, and write down that you did.
