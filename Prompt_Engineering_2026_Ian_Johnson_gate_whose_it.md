# Whose gate is it?

A talk at [Conf42 Prompt Engineering 2026](https://www.conf42.com/prompt2026) by [Ian Johnson](https://www.conf42.com/speaker_Ian_Johnson) (Staff Software Engineer @ Parento). Page: https://www.conf42.com/Prompt_Engineering_2026_Ian_Johnson_gate_whose_it

Video: https://www.youtube.com/watch?v=IiggBbE2j-g

## Abstract

Every team running coding agents already has all three. A charter that says what the repository is about, a harness that decides how a turn happens, and a factory that decides how work ships. Almost nobody has drawn the lines between them, so a new rule lands wherever the person who noticed the problem happened to have commit access. Platform ships a harness and finds one team's opinion inside it. Development writes a charter and spends a third of it trying to configure a pipeline it cannot reach.  So I will put the levers on screen, context by context, and then walk a single rule down the six rungs where a gate can physically sit. Two more rungs sit off that chain, and both stay off it for a reason. On the way down, the context changes under you three times, and so does the team that owns the file.  Then the part platform engineers came for. There are two boundary lines here, and most designs only draw one. The context line asks what a thing governs. The ownership line asks who gets paged when it is wrong. Both lines agree at the charter, which belongs to development, and both agree at the factory, which belongs to platform. They cross inside the harness, which is where your org-design arguments have been living all along. You leave with that split named component by component, and with the rule that makes shared ownership survivable.
