# Verification Timing: Why Checking AI-Written Code at the Gate Is Already Too Late

A talk at [Conf42 DevSecOps 2026](https://www.conf42.com/devsecops2026) by [Yunhao Jiao](https://www.conf42.com/speaker_Yunhao_Jiao) (CEO & Co-founder @ TestSprite). Page: https://www.conf42.com/DevSecOps_2026_Yunhao_Jiao_aicoding_verification_gates

Video: https://www.youtube.com/watch?v=FKRzJSMkLe8

## Abstract

Security gates were designed around a human pace. Someone writes code, opens a pull request, and a scanner or a reviewer inspects what arrived. That model quietly assumed the volume of code reaching the gate was bounded by how fast people type.

AI coding agents broke that assumption. They run unattended for hours, produce more change than any gate can meaningfully inspect, and they routinely break code they had already gotten working. In CoderCup, a public competition where four frontier coding agents built the same ten-phase application under identical rules, every agent broke previously working features between 31 and 57 times during a single build. Those breaks stayed invisible until something actually ran the application.

This talk is about verification timing. Not whether to verify, but when. Across CoderCup, agents got the task right on the first attempt about 80% of the time and reached 94% once a verification loop caught the failure and drove the fix. That gain happened inside the agent's own loop, before anything reached a pipeline. Verification that runs only at the gate arrives after the mess is already made. Give the agent those same checks while it works, so it finds each break and fixes each one before moving on.

Attendees will leave with a way to think about where verification belongs in an agent-driven pipeline, which two numbers are worth putting on a dashboard, and what evidence to demand from any tool claiming to check an agent's work.
