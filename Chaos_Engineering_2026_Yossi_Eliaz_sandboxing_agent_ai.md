# Sandboxing an AI Agent Is Not One Decision, It's Four

A talk at [Conf42 Chaos Engineering 2026](https://www.conf42.com/chaos2026) by [Yossi Eliaz](https://www.conf42.com/speaker_Yossi_Eliaz) (Head of DevRel @ Incredibuild). Page: https://www.conf42.com/Chaos_Engineering_2026_Yossi_Eliaz_sandboxing_agent_ai

## Abstract

Every framework that lets an AI agent write and run its own code eventually asks the same question: how much of that code should execute inside a sandbox, and how much stays outside as trusted orchestration. The common answer treats sandboxing as one API with one security level, pick a container image and move on. Real systems need at least four distinct boundaries, and they are not a ladder from less secure to more secure, each one isolates a different unit of work for a different reason. Restricted code orchestration keeps a credentialed agent in charge and lets it call only pre-registered tools, nothing new ever actually executes. Sandboxed code execution as a tool crosses a real line: model-generated code runs somewhere the credentialed agent cannot reach, called like any other tool. Sandboxed command execution moves an entire author-defined job into isolation, with its own lifecycle for files, artifacts, cancellation, and reconnection after a dropped connection. Sandboxed task execution goes further still, moving a worker's complete instruction set into a remote executor that owns the whole task lifecycle end to end. Picking the wrong boundary either leaves a real code-execution hole open or pays isolation costs a workload never needed. I will walk through this taxonomy using real, ongoing work inside Apache Airflow's agentic execution model, show a live example at each of the four positions, and give the audience a concrete way to reason about their own agent architecture instead of reaching for "just run it in a container."
