From Prototype to Millions of Daily Renders: Shipping LLM-Powered Features Reliably at E-commerce Scale

Artem ZamarajevSenior Software Engineer @ Amazon

    Hi, everyone. Thanks for joining. I'm Artem. I've been a software engineer for about 10 years, and I'm currently a senior software engineer at Amazon working on AI shopping features.

    So, here's the topic that I wanna talk about. Getting a model to produce good output in a demo isn't hard anymore, and the work is now serving that output on a high-traffic page without sl-slowing down the page and without showing customers something wrong.

    I have one note on the scope. So this talk is about AI features that live on a web page, the kind of a shopper loads in a browser, like a product page. If you're building a standalone chatbot or a background agent, some of this still applies, but a traditional web page is what I have in mind for this talk So you probably know the standard production toolkit. It's timeouts, caching, canaries, feature flags, dashboards, A/B tests. So LLM features add three problems on top of it. The first is latency. Google's guidance is that a page's main content should appear within two point five seconds, and that the first byte from the server should arrive in under zero point eight seconds. A fast model starts streaming in a few hundred milliseconds, but a full response usually takes several seconds, and the slow tail runs well past that.

    The second is quality. Bad output usually comes back well-formed with a successful status, so your error rate stays flat while customers read something wrong.

    The third is cost. Every call costs money and at page view volume, that can add up.

    So the four lessons that follow are about these three problems So I've grouped this into these four lessons. They follow the life of a feature. So it's deciding when to generate, serving the output, checking it, and connecting to the assistant.

    All of this is model agnostic To keep this simple, I'll use one example throughout. Ridgeline Coffee, a made-up store.

    Ridgeline wants three LLM features on its product pages. The first is a quick take. It's three short highlights about the coffee written by an LLM It uses product details and reviews to get this information. It shows on every product page. The second is suggested questions. A few questions picked for this shop are like, "Is it similar to the Colombia I bought last time?" They also show on every product page, and tapping one asks the store's AI assistant. The third is an Ask button. It opens the same assistant, which already knows which coffee you're looking at, so you can ask your own questions like, "Will this work for espresso?" So these are the two kinds of AI features I'll keep coming back to. The quick take is pre-computed. It's generated ahead of time, and the page only reads stored text.

    The suggested questions and ask button are live. They call the model while the shopper is on the page. Each kind runs into different problems, so for every lesson, I'll say which kind it is about.

    Lesson one: precompute by default. So the problem is when you're doing a demo, right, you're most likely just doing a live call to LLM.

    But then if you just put it to production, now every page would wait for a model call that takes seconds and costs money, and for some features, the output would be the same for every shopper. And so before building a feature, it's worth asking whether it has to be generated while the shopper waits. So there's three questions that decide it. Does the output depend on the shopper or what they typed? How often do inputs change? And is anyone waiting for it? So the quick take is the same for every shopper. It changes only when the product or its reviews change, and nobody's waiting for it. So we generate it in a background job, run the checks, and store the default.

    At page load, the page does a key lookup. The ask button can't be precomputed because the response depends on the question. It runs live, but only for the shoppers who click, which is usually a small share of page views.

    Suggested questions depend on the shopper, and there are too many shoppers and product pairs to generate them all ahead of time, so they run live too on every page view.

    So keep that in mind for lesson four.

    So this works because a precomputed feature puts no model call on the page at all. Latency becomes just a key lookup, and cost follows product changes instead of traffic.

    So the LLM part becomes a content pipeline, which is a, an easier to deal with problem.

    One thing to get right is when to regenerate. If you regenerate on every new review, a popular product burns model calls all day for output that barely changes. So a threshold, like a minimum number of new reviews or a change to the product details, keeps costs tied to real change. I start from precomputed and see if the feature really needs to be real time Lesson two, keep the model off the critical path. So the problem is that a model call takes seconds and sometimes fails. If the page waits for it, the page is as slow and as fragile as this model call. So the usual protection, a timeout, doesn't help much here. A timeout short enough to protect the page would cut off most of model calls.

    So the fix depends on the kind of feature. A pre-computed feature already reads stored text, so the open question is what to show when nothing good is stored.

    Decide that before you write a single prompt. I think of it as a ladder. So fresh content first. If that's missing or failed a check, the last good version you saved. If there's none, a plain non-AI default, like the product's existing bullet points. And as a last resort, just hide the feature. For live features, render the page first and call the model afterwards. The Ask button calls it only after the shopper asks. Suggested questions fill in after the page has loaded, and if they're slow or fail, that space stays empty. For Ask, stream the response. The first words appear long before the full response would, and streaming keeps long responses from hitting fixed timeouts in proxies and gateways.

    This works because the page never waits on the model. Whether the model is slow, failing, or down, the page loads, and the worst case is a plainer page Lesson three, check outputs before customers see them So the problem is that wrong output from a model could look like success. It's well-formed, the call returns fine, and your error dashboard stays flat, and the company owns it either way. So there was an interesting case in two thousand twenty-four, a Cana- Canadian tribunal ruled against Air Canada after its chatbot told a customer that he could claim a bereavement discount after his trip, which contradicted the airline's own policy page. But the tribunal held the airline responsible for what the chatbot said, the same as for any other page on its site.

    So the fix for a precomputed feature like quick take is check four things before storing it.

    Format so it renders, grounding so every claim traces back to the product data or a review, consistency with the rest of the page. A highlight that says the coffee ships ground on a page that says whole bean only is the kind of the problem that Air Canada had at a smaller scale.

    And the content policy. Format and policy are mostly simple rules. Grounding and consistency often need a second model call to judge the first. Anything that fails goes down the fallback ladder from lesson two This works because that output is caught before it's stored, so it never reaches the page, and the extra model call is affordable because you pay for it once per product change, not once per page view.

    Live responses are harder because there's no time to run all of that before the first word appears, so the fix comes in layers. Keep the model working from the product's own data so grounding is built in.

    Run cheap rule-based checks on the stream and stop or respl-- replace response that fails one. Afterwards, judge a sample of real responses with the same checks you use for precomputed content. That catches problems in aggregate, not one response at a time, which is why live features also need a narrower scope and an easy way for shoppers to report a bad response.

    For both precomputed and live features, keep an eval set, a fixed set of real products with known good and known bad outputs rerun on every prompt or model change. And in production, watch the rejection rate, especially while prompt or model change is rolling out. The page will look healthy because the fallbacks cover for failures, so moving rejection rate is often your first sign that something changed Lesson four: put one service in front of the assistant. This one is about live features. So for Ridgeline Coffee, two features call the same assistant, the Ask button and the suggested questions. The first problem is duplicated rules. When each feature calls the assistant directly, each one keeps its own copy of the rules, which pages and shoppers are eligible, which languages are supported, which timeout to use, and what to show when the call fails.

    Those copies could drift apart into features on the same page start behaving differently.

    Second problem is capacity.

    Let's say the assistant was first built for the Ask button, so it's sized for the shoppers who click it, which is a small share. Suggested questions appear on every product page, so they call the assistant on every page view. Launching them can multiply the assistant's traffic.

    So the fix is a small service between the features and the assistant. Features don't call the assistant directly, they call the service. And the service, it holds the eligibility rules, sets the timeout, and returns a fallback when the assistant fails. It also gives each feature a traffic budget and rate limits any feature that goes over it.

    I make it a service rather than a shared library because a library can't enforce one budget across every caller.

    This works because the rules live in one place, so they cannot drift. Every calls goes through one door, so no feature can send page scale traffic to the assistant without someone planning for it.

    If the assistant slows down, the service returns fallbacks, and the pages are fine. If a feature misbehaves, its budget stops it before it reaches the assistant So if there's one thing you remember from this talk, it's calling the model is easy, and most of the work is just a system around it.     Abstract

    Getting an LLM-powered feature to work in a demo is easy. Serving it on a high-traffic e-commerce page millions of times a day, without hurting latency or showing customers a bad answer, is a different job.

    Drawing on shipping AI shopping features at Amazon that reached millions of daily page renders with zero faults, this talk covers the operational side of putting generative AI on a critical page:

    • Deciding when content should be generated in real time and when it can be precomputed
    • Latency budgets, timeouts and fallbacks so the page never waits on a model
    • Quality gates and monitoring that catch bad output before customers see it
    • Integrating with an existing AI assistant’s orchestration without becoming its bottleneck
    • Launching safely: gradual dial-ups, kill switches and the metrics that matter

    Attendees leave with a practical checklist for taking an LLM feature from prototype to production traffic.
